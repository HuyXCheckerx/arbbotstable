**Arbbot code audit — 28 September 2026**

The repository has useful safety components, but they do not form a consistent execution system. The highest priorities are repairing the default quote bridge, serializing wallet submissions, preserving unresolved transactions, and making the configured profit policy match the actual execution gates. Formatting is a lower priority.

This review examined the orchestration, Ethereum and Solana atomic engines, multichain engine, Solidity executors, legacy Solana scanner, recovery/state modules, dashboard, launchers, provider adapters, and selected supporting scripts. The bundled `vietdefi` and `meta-matcha` apps received a targeted review, not a complete application audit. This is source review and local verification; deployed bytecode, live liquidity, real provider acceptance, and real-world profitability were not verified. No trading, deployment, proxy purchasing, or live scanner was started. No implementation code was changed.

**Verification evidence**

- Python: `.venv/bin/python -m unittest discover -s tests -p 'test_*.py'` — 286 tests passed in 21.302 seconds.
- TypeScript: `npm test` — typecheck passed and 40 tests passed.
- Additional AST parsing found three invalid Python files: the production browser bridge and two scratchpad scripts. Passing unit tests therefore do not establish that all production modules can load.
- An isolated execution of the actual profit-scaling helper reduced a 5.000001-unit floor to 0.050000 on a 1,000-unit trade with a 100,000-unit base.
- Generated minimal-proxy runtime contains neither selector required by the engine's stable-first capability detection.
- A temporary malformed recovery file was interpreted as no active recovery, rather than a blocking state error.
- Inventory of 123 tracked source files: 42,519 lines, 165 lines with trailing whitespace, 177 lines longer than 120 characters, and no tab-indented lines. These counts include tests and auxiliary applications.

**1. High — the default browser bridge cannot be imported**

Evidence: [matcha_browser_bridge.py:514](/Users/perycent/Downloads/arbbot/src/engines/matcha_browser_bridge.py:514), [Ethereum bridge selection:1263](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:1263), [Solana bridge selection:295](/Users/perycent/Downloads/arbbot/src/engines/metamatcha_solana.py:295).

Python reports `SyntaxError: expected 'except' or 'finally' block` when parsing the bridge. The preceding worker has an unfinished outer `try`. Real clients select the bridge by default; its import handlers catch `ImportError`, which does not catch this `SyntaxError`. Startup catches the initialization failure, but that does not repair the quote path. Affected real route requests can fail while mocked tests pass.

Repair the syntax and add syntax checks plus import smoke tests for every production module. Mock the transport beneath the real adapter so integration tests actually execute the selected provider path. Exclude archived scratchpads explicitly, or rename them as text instead of leaving invalid executable Python.

**2. High — parallel scanning also executes transactions concurrently**

Evidence: [worker:1795](/Users/perycent/Downloads/arbbot/src/engines/crosschain_sniper.py:1795), [nonce selection:2088](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:2088).

The scheduler submits up to six route checks concurrently and forwards `live=True` into each. These are full quote-to-broadcast operations. Ethereum obtains the transaction count without specifying `pending` and without a shared nonce reservation. Two profitable routes can independently sign different transactions with the same nonce. This can produce replacement errors, conflicting private submissions, or the wrong route winning. Solana routes similarly contend for shared wallet balances, pools, and Marginfi accounts.

Keep quote collection concurrent, but put final validation, funding reservation, signing, and submission behind a per-chain/per-wallet coordinator. Use a persistent nonce reservation, initialized from pending state and reconciled with existing private submissions. A `pending` RPC lookup alone is insufficient when several workers call it simultaneously. Recheck route validity immediately before signing. Add a barrier-based test in which two eligible routes reach execution at the same instant.

**3. High — the atomic engines do not durably record intent before broadcast**

Evidence: [Ethereum send:2837](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:2837), [Ethereum receipt persistence:1690](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:1690), [Solana send:3350](/Users/perycent/Downloads/arbbot/src/engines/solana_flash_arb.ts:3350), [submission handling:1645](/Users/perycent/Downloads/arbbot/src/engines/crosschain_sniper.py:1645), [startup reconciliation:2116](/Users/perycent/Downloads/arbbot/src/engines/crosschain_sniper.py:2116).

Both engines attach the local hash/signature to their plan only after the broadcaster returns. If a node accepts the transaction and its response is lost, or the process dies during the call, the durable plan can lack the identifier needed to reconcile it. The sniper treats a known unresolved submission as a short cooldown, and startup merely logs a previous unresolved submission and continues. A later route can overwrite the route's plan file.

Ethereum additionally labels a transaction dropped when one RPC cannot find it and reports an unused nonce. With Flashbots/private relays, that public RPC may never have seen a still-live transaction. This is evidence of local absence, not proof that private submission has expired.

Persist a unique attempt with chain, wallet, local transaction identifier, nonce/blockhash, expiry, and broadcast destination before any network send. Make state transitions transactional: prepared → submitted/unknown → confirmed/reverted/expired. Block dependent wallet submissions until reconciliation resolves uncertainty. Treat private expiry and cancellation explicitly. The legacy Solana engine's pre-broadcast pending record is a useful starting pattern.

**4. High — “guaranteed net profit” overstates the Ethereum protection**

Evidence: [Matcha quote parsing:734](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:734), [stable-first gross:2465](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:2465), [cost calculation:2688](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:2688), [on-chain balance check:535](/Users/perycent/Downloads/arbbot/contracts/MorphoMatchaStableArbUsdc.sol:535).

The stable-first path calculates gross from quoted `buyAmount`. The parser does not retain a separately verified executable minimum output. The contract receives the gross minimum, while gas/native costs are deducted only in the off-chain eligibility check. A simulation is a point-in-time result, not a guarantee of the eventual output or net profit.

Example: quoted gross 8, budgeted costs 2, required net 5 passes off-chain. If execution returns gross 5.5 and costs 2, the transaction can satisfy a gross on-chain floor of 5 while realizing net 3.5. This scenario depends on the route's encoded output bounds permitting that movement; the current parser does not establish the stronger net invariant.

Define expected output, executable minimum output, gross profit, maximum execution cost, and realized net as separate fields. Require the on-chain gross floor to cover required net plus conservatively budgeted execution costs. Rebuild and simulate with the final floor. Validate actual calldata output constraints. Label estimates accurately in the UI. USD conversions also need an explicit stablecoin valuation policy rather than silently equating token units with guaranteed dollars.

**5. High — the minimum-profit setting changes meaning across layers**

Evidence: [chain threshold override:227](/Users/perycent/Downloads/arbbot/src/engines/crosschain_sniper.py:227), [Ethereum scaling:621](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:621), [Solana scaling:3105](/Users/perycent/Downloads/arbbot/src/engines/solana_flash_arb.ts:3105).

The sniper converts a threshold of 4 or 5 into 1 for Solana. Both atomic engines then scale the floor down with principal. The actual helper turns 5.000001 into 0.050000 at 1,000/100,000 size. This contradicts the README's strict absolute five-unit example, and the dashboard records the unscaled route execution floor. Some code and tests intentionally describe proportional scaling, so the defect is also a policy/documentation inconsistency, not merely a missing comparison.

Expose separate settings for absolute minimum net profit and minimum return in basis points. Compute the requirement as the maximum of the two. If proportional operation is intended, name it explicitly and display the exact effective threshold used by the engine. Eliminate magic special cases for thresholds 4 and 5. Test equality and one raw unit either side of the boundary after sizing.

**6. High — the engine rejects stable-first execution through its own minimal proxies**

Evidence: [bytecode inspection:1989](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:1989), [proxy construction:96](/Users/perycent/Downloads/arbbot/src/deployers/deploy_proxy_executor.py:96).

The engine searches the executor's runtime bytecode for `blacked` or the explicit swap-order function selector. An EIP-1167 proxy holds a delegatecall stub and an implementation address, not its implementation's function dispatcher. Generated proxy runtime fails both checks, and the fallback branch accepts only dex-first. The automatic rotation mechanism can therefore deploy a proxy that the stable-first path immediately declares incompatible.

Use an explicit version/capability interface, or resolve the recognized proxy implementation before validating code identity. Verify owner, chain, implementation hash, token support, flash-provider support, and swap-order support together. Exercise both directions against an actual local clone. Do not assume that searching arbitrary bytecode for four bytes establishes ABI compatibility.

**7. High — dry-run orchestration can perform paid administrative actions**

Evidence: [proxy startup:2175](/Users/perycent/Downloads/arbbot/src/engines/crosschain_sniper.py:2175), [automatic purchase:493](/Users/perycent/Downloads/arbbot/scripts/manage_proxyisp.py:493), [automatic deployment branch:1715](/Users/perycent/Downloads/arbbot/src/engines/crosschain_sniper.py:1715), [rotation:103](/Users/perycent/Downloads/arbbot/src/engines/proxy_executor.py:103).

The startup proxy manager can purchase a new residential proxy when an API key is configured and no existing proxy passes. That call is independent of `args.live`. The blocked-taker outcome handler can deploy a replacement executor and restart the entire process without a live-mode argument or explicit maintenance gate. The current bridge syntax defect may prevent this deployment path from being reached successfully; the unsafe control flow remains once the bridge is repaired.

Separate monitoring/trading from infrastructure maintenance. Dry-run must prohibit spending and signing across the entire call graph. Add explicit maintenance policy, spending limits, deployment cooldowns, and a drain-and-stop procedure before replacing a process with in-flight work. A failed taker probe should report unknown separately from a confirmed access denial; timeouts must not be treated as proof of a blacklist.

**8. High/medium — private submission implementations are incomplete**

Evidence: [embedded Flashbots signing:1647](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:1647), [existing corrected helper:39](/Users/perycent/Downloads/arbbot/flashbots_relay.py:39), [Jito broadcaster:2898](/Users/perycent/Downloads/arbbot/src/engines/solana_flash_arb.ts:2898).

The active Ethereum relay branch signs the raw digest using `encode_defunct(body_hash)`. The repository already contains a corrected relay helper that signs the digest's hex text, but the engine does not call it. Flashbots documents text-based signing in its [authentication specification](https://docs.flashbots.net/flashbots-auction/advanced/rpc-endpoint#authentication). The Protect RPC branch is separate; this finding specifically concerns the authenticated relay fallback.

The Solana broadcaster submits `sendBundle` but does not construct or verify a Jito tip; its tip-address constant is otherwise unused. It also discards the returned bundle ID after logging it and returns immediately on acceptance. Jito says bundles require a tip, documents a 1,000-lamport minimum, and distinguishes acceptance from landing in its [submission documentation](https://docs.jito.wtf/lowlatencytxnsend/). Provider-supplied instructions could happen to contain a tip, but this engine does not ensure one exists or account for it.

Consolidate the Flashbots implementation. Add explicit private-only versus public-fallback policy, bounded network deadlines, bundle status/expiry handling, and verified tip instructions included in costs. Test successful private submissions and delayed landing, not only public fallback after a mocked exception.

**9. High, conditional on bad provider data — Solana signs instructions without a complete spending policy**

Evidence: [MetaMatcha instruction extraction:1789](/Users/perycent/Downloads/arbbot/src/engines/solana_flash_arb.ts:1789), [wallet-funded transaction:2194](/Users/perycent/Downloads/arbbot/src/engines/solana_flash_arb.ts:2194), [simulation:2240](/Users/perycent/Downloads/arbbot/src/engines/solana_flash_arb.ts:2240).

The engine checks payer/signers, strips compute-budget instructions, and simulates, but otherwise retains supplied instructions. Simulation checks transaction errors and compute usage; it does not verify that only the intended wallet assets/amounts were spent. A successful simulation alone would not reject an unrelated transfer, approval, or authority operation bundled with a swap. Automatic wallet-funded execution increases the importance of this boundary.

Validate permitted programs and sensitive instruction types, asset accounts, exact input limits, recipients, and account ownership. Check simulated balance changes and protect the final balance invariant on-chain where feasible. Keep signing isolated from quote helpers. This is a missing defense demonstrated by code inspection, not a claim that a current provider is malicious or that funds have been stolen.

**10. High/medium — recovery state can fail open, and recovered inventory lacks durable ownership**

Evidence: [recovery read:38](/Users/perycent/Downloads/arbbot/src/recovery/recovery_store.py:38), [startup inventory adoption:1590](/Users/perycent/Downloads/arbbot/src/engines/swapstable.py:1590), [recovery confirmation:92](/Users/perycent/Downloads/arbbot/src/recovery/recovery_worker.py:92).

Malformed, unreadable, or unsupported recovery state becomes an empty default. The temporary-file reproduction returned `None` for active recovery after deliberately corrupting JSON. This can discard the pending-transaction guard. The scanner can also adopt the entire intermediate-token wallet balance as recovery inventory, rather than a durable amount owned by a particular attempt. The README's promise to preserve pre-existing balances is consequently not a global invariant.

Distinguish missing fresh-install state from corrupt existing state. Corruption must block spending until reconciliation, retaining the damaged file. Persist position baselines and per-attempt inventory ownership. Recovery needs an exclusive execution lease, not only locks around individual JSON mutations, and a confirmed partial exit must retain the exact remainder through restart. Review the restart confirmation check, which compares remaining wallet balance with the full planned amount rather than tracking the submitted partial amount explicitly.

**11. Medium — accounting does not cover the complete execution lifecycle**

Evidence: [legacy attempt ledger:505](/Users/perycent/Downloads/arbbot/src/core/state_store.py:505), [recovery completion:402](/Users/perycent/Downloads/arbbot/src/recovery/recovery_worker.py:402), [atomic engine receipt:1690](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:1690).

The legacy scanner records attempts in SQLite. Atomic engines primarily retain per-route plans and receipt/status information; their reported net is predicted. The recovery worker completes its own plan without recording a linked P&L/fee event in the attempt ledger. This does not establish an end-to-end realized result across entry, failed legs, subsequent recovery, setup transactions, and infrastructure costs.

Use one append-only attempt/transaction ledger across engines with stable IDs. Track expected versus realized token deltas, native fees, tips, setup/rent effects, flash premiums, provider/native charges, and recovery linkage. Aggregate those events into dashboard projections. Preserve raw integer quantities and explicit prices; round only for display. Attribute external wallet transfers separately. The SQLite JSON fallback also deserves fail-closed treatment if it contains pending-submission state.

**12. Medium — credential-bearing URLs enter operational logs**

Evidence: [proxy logging:530](/Users/perycent/Downloads/arbbot/scripts/manage_proxyisp.py:530), [dashboard log endpoint:697](/Users/perycent/Downloads/arbbot/src/web/web.py:697), [default bind:30](/Users/perycent/Downloads/arbbot/src/web/web.py:30), [Solana endpoint logging:2941](/Users/perycent/Downloads/arbbot/src/engines/solana_flash_arb.ts:2941).

Proxy setup logs formatted URLs containing username/password. When invoked by the sniper it uses the sniper logger, and the dashboard returns that log tail without redaction. Directly starting `src/web/web.py` binds to all interfaces by default; the preferred launcher can use a safer host. Solana also prints a raw RPC URL, which may contain an API credential. Actual exposure depends on the chosen bind and network access, but secrets should not enter these logs at all.

Use one redaction function for URLs, headers, and exception text at every log boundary. Default every launcher to loopback and use authentication for remote dashboard access. Add fixture tests containing dummy credentials and assert they cannot appear in logs or API responses.

**13. Medium — timeout, health, and request-spacing policies are inconsistent**

Evidence: [direct Ethereum runner:1103](/Users/perycent/Downloads/arbbot/src/engines/crosschain_sniper.py:1103), [parallel scheduler:1839](/Users/perycent/Downloads/arbbot/src/engines/crosschain_sniper.py:1839), [direct-provider pacer:71](/Users/perycent/Downloads/arbbot/src/engines/direct_aggregators.py:71), [health state:176](/Users/perycent/Downloads/arbbot/src/web/web.py:176).

The direct Ethereum runner accepts `timeout_seconds` but never applies it as an overall deadline. A parallel batch schedules all eligible routes before its failures update cooldowns, so queued work can continue using a provider after access denial. A cooldown is not cancellation. Jito's fetch has no explicit abort timeout. The dashboard treats a live PID as healthy even if the feed/worker is stalled.

Use monotonic deadlines passed through quote, simulation, and submission stages. Add provider-wide bounded queues and rate limits shared by all routes and processes where appropriate. Recheck breaker state at dispatch, honor Retry-After, add jitter, and distinguish quote freshness from request timeout. The existing direct-provider pacer is useful, but does not by itself coordinate every engine or child process. Split liveness from readiness and alert on stale feed age, last successful check, pending age, queue length, latency, and recent errors.

**14. Medium — test doubles change production behavior**

Evidence: [subprocess detection:1092](/Users/perycent/Downloads/arbbot/src/engines/crosschain_sniper.py:1092), [runtime dispatch:1263](/Users/perycent/Downloads/arbbot/src/engines/crosschain_sniper.py:1263), [HTTP mock detection:991](/Users/perycent/Downloads/arbbot/src/engines/eth_flash_arb_pyusd_usdc.py:991).

Production code detects mocks and selects different engine, browser, or retry behavior. This explains how the broken bridge escapes a green suite. The tests are valuable for arithmetic and local helpers, but the passing count should not be treated as execution-path coverage. No dedicated Solidity test harness was found in the repository.

Inject explicit interfaces for clock, transport, quote provider, signer, and broadcaster. Keep production branching identical in tests. Add representative provider fixtures, startup smoke tests, concurrency tests, interrupted-broadcast tests, and local EVM contract tests. Test unauthorized callbacks, wrong chain/owner, premiums, deadlines, pre-existing balances, reentrancy, approvals, both swap orders, and clone behavior. Run checks in CI; typecheck standalone TypeScript scripts as well as the main engine/test import graph.

**15. Medium — auxiliary apps silently substitute simulated success**

Evidence: [local MetaMatcha fallback:125](/Users/perycent/Downloads/arbbot/meta-matcha/server.py:125), [CAP verification fallback:87](/Users/perycent/Downloads/arbbot/vietdefi/src/services/capService.ts:87), [tax inventory logic:43](/Users/perycent/Downloads/arbbot/vietdefi/src/services/taxService.ts:43).

The local MetaMatcha server generates synthetic quotes when upstream fails. The VietDeFi CAPTCHA client returns success for any fresh nonempty token when verification fails or is unavailable. Its in-memory replay set is client-controlled. These are demonstrations, not suitable production trust boundaries. There is no evidence from this review that either auxiliary app is wired into the sniper's default path.

Make demo mode explicit and visibly labeled; never substitute simulated market data or authorization success on a production error. Enforce CAPTCHA authorization and replay prevention server-side. The tax calculator also filters out prior-year inventory before computing FIFO, does not sort transactions, and does not implement the named alternative basis methods. Separate these apps from the trading deployment. Its legal assumptions were not validated in this engineering review.

**Structure, spacing, and maintainability**

The largest Python function is `swapstable.main`: 1,743 lines. The primary Ethereum `run` is 571 lines. Core runtime/contracts alone exceed 22,000 lines. Similar parsers, HTTP clients, transaction builders, environment readers, and errors appear in several engines. Repeated `sys.path` mutation and a mixture of qualified/bare imports make module identity and test patching fragile. Some root wrappers execute on import; the root Solana wrapper imports the engine without triggering its guarded `main`, so it is not equivalent to the canonical CLI entry point.

Move toward a package with small, explicit boundaries: configuration; chain adapters; quote providers; pure sizing/profit logic; execution coordinator; broadcaster/reconciler; durable ledger; dashboard projections. Replace log-message regex classification with typed outcomes. Keep optional provider fallbacks declared in configuration. Centralize contract addresses and validate them: the current config registry and primary engine/Solidity source disagree on the Stable pool address, so the supposedly centralized registry is not actually authoritative.

For code spacing, use four-space Python indentation and the existing two-space TypeScript convention. Add deterministic format/import checks, remove trailing whitespace, and choose one line-length policy. No tab-versus-space indentation problem was detected. Keep mechanical formatting in a separate change from transaction logic so reviewers can see the meaningful safety changes.

For trade/request spacing, define independent settings for per-provider request pacing, per-route scheduling, post-execution wallet cooldown, and unresolved-transaction blocking. Do not encode all four through sleeps. Parallel quotes should feed a serialized execution decision. Cache slow-changing metadata and reuse connections, but impose explicit freshness limits on prices, capacity, gas, blockhashes, and executable quotes. Rank candidates by conservative net after provider-specific cost, not raw buy amount with gas only as a tie breaker. Consider bounded size optimization in the atomic engines instead of only shrinking to available capacity.

**Suggested implementation order**

1. Repair bridge syntax and add production-module parse/import checks. Remove mock-dependent routing.
2. Introduce durable transaction intent plus per-wallet execution/nonce coordination. Correct private-submission reconciliation and ambiguous-state blocking.
3. Define one explicit profit policy, use executable minimum output, and enforce the intended net floor through the final transaction.
4. Repair clone capability checks and private broadcaster integrations. Gate all administrative spending separately from monitoring.
5. Harden Solana instruction validation and recovery ownership/corrupt-state behavior.
6. Unify realized accounting, redact credentials, and add meaningful readiness/latency metrics.
7. Consolidate adapters/configuration, separate demos and scratchpads, add CI and contract tests, then apply formatting.

Useful existing work to retain includes the Solidity owner/callback/phase checks, exact approvals followed by resets, pre-existing loan-balance protection, raw-unit sizing helpers, legacy pre-broadcast pending records, WebSocket revision tracking, SQLite WAL-backed accounting, atomic dashboard snapshots, and the read-only dashboard endpoint. The improvement is to extend these guarantees consistently across every live path.
